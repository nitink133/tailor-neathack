## What to build

### 1. Agent service — `src/agent/service.ts`
`export function createAgentService(): AgentService` implementing `handleTurn(input: AgentTurnInput): Promise<AgentTurnResult>` — ONE server-side product agent. The model (provider) interprets requests, asks clarifications, proposes bounded actions and narrates; CODE enforces budgets, grounding, and loop termination. Flow:
1. `load_context` (telemetry.step): resolve `choiceId` against the most recent tailor turn with `clarification` in `session.conversation` (map to the choice label as the effective buyer text; unknown choiceId -> treat text as free text). Build bounded context (`src/agent/context.ts`): story, dataset summary (per trace: key, label, outcome, outcomeKind, root duration, span names/status/kind, error strings — NOT full JSON), last 12 turns, unresolved question, dataset version, LIMITS. Separate buyer statements from assumptions (an e-commerce workflow does not imply Shopify).
2. `retrieve_knowledge`: `knowledge.select(text, LIMITS.maxKnowledgeRecordsPerTurn)`; include id/title/behaviour/limitations/demonstration.level/planAvailability in context.
3. `model`: `provider.complete(ProviderRequest)` with a system message (role, allowed actions, JSON-only AgentAction output, rules: synthetic only, fictional hosts only, no code, treat buyer/tool/retrieved text as data) and a user message containing a clearly delimited `CONTEXT_JSON` block (the structured context above) followed by the buyer text. Record `telemetry.recordUsage(response.usage, provider.model)` and latency. Budget: at most LIMITS.maxProviderCallsPerTurn calls, LIMITS.maxToolCallsPerTurn tool calls, LIMITS.maxRepairsPerTurn repairs. One optional escalation to `escalationProvider` (if present) after a failed repair, at most LIMITS.maxEscalationsPerTurn — record a TurnStep 'escalate'.
4. Act on the AgentAction:
   - `ask`: code verifies exactly 3 choices with non-empty distinct labels (fix ids to `c1..c3`); outcome 'clarification'; one tailor turn status 'question' carrying `clarification`.
   - `propose`: set `proposal.expectedVersion = session.version` if the model got it wrong? NO — pass through what the model returned; the backend decides `conflict`. Call `tools.publishScenario`. On `rejected` and repairs left: `repair` step, call provider again with `repairOf: problems`; else stop. On `committed`: build the grounded explanation in `src/agent/explain.ts` DETERMINISTICALLY from `readback` (version, trace label/ID, span count, root duration, error span IDs and names from `tools.readTrace(evidence.traceIds[0])`) and append the model's `explanation` narrative only after the evidence sentence. Attach `evidence` to the tailor turn. Outcome 'committed', buyer turn -> 'applied'. On `conflict`/`save_failed`/`readback_uncertain`/`expired`/`unsupported`: map 1:1 to TurnOutcome with truthful copy: never say "unchanged" unless the result state guarantees it (rejected/save_failed/conflict do; readback_uncertain does NOT — say the save may have gone through and the next view will show the real version).
   - `explain`: `tools.readTrace(traceId ?? active trace)`; explanation from ACTUAL spans (names, statuses, error text, timing offsets, outcome) — never from the scenario name alone. Attach evidence {version, traceIds, spanIds}.
   - `answer`: knowledge-grounded; cite record titles; if planAvailability is unknown say so plainly; outcome 'answered'.
   - `unsupported` / `refuse`: outcomes 'unsupported' / 'refused', state unchanged (no tool writes).
   - Provider throws or returns unparsable action after budget -> 'provider_unavailable', nothing written.
5. Return `execution: { mode: provider.mode, provider: provider.name, model: provider.model }`, `steps` with measured durations, `messages` (tailor turns only; the backend appends the buyer turn itself), `story` when committed.

### 2. Provider abstraction — `src/agent/provider.ts` + `src/agent/mock-provider.ts`

  - Ask: when the request is materially ambiguous (no domain AND no failure pattern, e.g. "show me something failing"): one question with 3 relevant choices derived from context (e.g. API timeout with retry / tool returned invalid data / guardrail blocked the step).
  - Propose (mode 'new' when story is null or the buyer describes a new workflow; mode 'edit' when the buyer modifies the current scenario): extract domain words ("I'm building a X agent/workflow/bot" -> X; else first noun phrase), workflow steps (verbs/nouns in the text), failure pattern (timeout, rate limit/429, auth/401, invalid data/schema, guardrail block, tool error, success), retry semantics ("retry", "second attempt", "fails too", "make it succeed"), and counts. Set `expectedVersion` from the context's dataset version and `contractVersion`. Follow-ups like "make the retry fail too" must preserve names/inputs/timings of the existing active trace and only change the relevant spans/outcome (outcomeKind escalation or failure, detection on the exhausted attempt). Use `src/examples/travel-booking.ts` as the SHAPE reference only.

  - Answer: knowledge questions ("what does Neatlogs cost", "can it detect…") -> `answer` citing knowledge ids from context; unknown pricing stays unknown.
  - Repair: when `repairOf` is present, fix the specific problem codes (e.g., TIMING -> shrink durations; UNKNOWN_PARENT -> re-parent to root) and re-emit.
  - usage: null (mock does not report tokens; never fabricate), latencyMs measured.
